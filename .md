# Access Tokens and Refresh Tokens: What I Understood

When I first started learning authentication, I thought it was mainly
about checking a username and password. After learning about access
tokens and refresh tokens, I understood that login is only one part of
authentication. The application also needs a way to identify an
authenticated user when that user makes requests later.

This article is about what I understood from learning this topic and how
I now understand the difference between access tokens and refresh
tokens.

## What happens after login?

Suppose I log in to an application with my email and password.

The server checks whether the credentials are correct. If they are
correct, the server can issue tokens that the application uses for
authenticated requests.

The two tokens I learned about are:

-   Access Token
-   Refresh Token

They have different jobs, even though both are related to
authentication.

## What is an Access Token?

An access token is a credential that allows a client to access protected
resources or APIs.

For example, a request to a protected API can look like this:

``` http
GET /api/profile
Authorization: Bearer <access_token>
```

The server checks the token before allowing the request.

The easiest way I remember it is:

**Access Token = permission to access protected APIs.**

Access tokens are normally short-lived. The exact lifetime depends on
the application and its security requirements.

## Why does an Access Token expire?

At first, I had a simple question: if the token is working, why not keep
it valid for a long time?

The main reason is security.

If an access token is stolen, anyone who has it may be able to use it
until it becomes invalid. A shorter lifetime can reduce the amount of
time a stolen access token remains useful.

So there is a balance:

-   Longer lifetime can be more convenient.
-   Shorter lifetime can reduce the exposure period if the token is
    compromised.

But a short-lived token creates another problem. If it expires, the user
should not have to enter their password again every few minutes.

That is where refresh tokens come in.

## What is a Refresh Token?

A refresh token is used to obtain a new access token after the current
access token expires.

A simplified flow looks like this:

``` text
User logs in
     ↓
Authentication server
     ↓
Access Token + Refresh Token
     ↓
Access Token is used for API requests
     ↓
Access Token expires
     ↓
Refresh Token is used
     ↓
New Access Token
```

The simple definition I use now is:

**Refresh Token = a credential used to get a new access token.**

The refresh token is not normally sent with every API request. It is
handled separately from the access token and needs careful protection.

## Access Token vs Refresh Token

  -----------------------------------------------------------------------
  Access Token                        Refresh Token
  ----------------------------------- -----------------------------------
  Used to access protected APIs       Used to obtain a new access token

  Usually short-lived                 Usually longer-lived

  Commonly sent with API requests     Used mainly with the token refresh
                                      process

  Gives access to protected resources Helps maintain an authenticated
                                      session
  -----------------------------------------------------------------------

This difference was probably the most important part of the topic for
me.

## A simple example

Imagine that I am using an e-commerce website.

I log in successfully and receive an access token and a refresh token.

When I open my profile, the application sends the access token with the
request:

``` text
Client
  ↓
Access Token
  ↓
Profile API
  ↓
User Profile
```

Later, the access token expires.

Instead of immediately asking me to log in again, the application can
use the refresh token to request another access token:

``` text
Client
  ↓
Refresh Token
  ↓
Authentication Server
  ↓
New Access Token
  ↓
Continue using the application
```

This is how the application can keep the user signed in while still
using short-lived access tokens.

## What if the Refresh Token expires?

A refresh token is also not permanent.

If it expires, is revoked, or becomes invalid for another reason, the
application may require the user to authenticate again.

So the flow can eventually become:

``` text
Access Token expires
        ↓
Refresh Token
        ↓
New Access Token
        ↓
Access Token expires again
        ↓
...
        ↓
Refresh Token becomes invalid
        ↓
Login required again
```

This gives the application more control over how long a user's
authenticated session can continue.

## Why not use only one token?

This was another question I had while learning the concept.

If a refresh token can help get a new access token, why not just use the
refresh token for every request?

The reason is that the two tokens have different purposes.

The access token is designed for normal API access and can be
short-lived. The refresh token is used less frequently and can be
protected more carefully.

Separating these responsibilities helps create a better security model.

## Token security

Learning about tokens also made me realize that simply using tokens does
not automatically make an application secure.

The application needs to consider things such as:

-   HTTPS
-   Token expiration
-   Secure token storage
-   XSS protection
-   CSRF protection where relevant
-   Refresh-token rotation or revocation
-   Proper validation on the server

For web applications, developers may use secure, HttpOnly cookies for
some authentication credentials. The exact design depends on the
application's architecture and threat model.

## What happens if a token is stolen?

This is an important security problem.

If an attacker gets a valid access token, they may be able to make
authenticated requests until that token expires or is otherwise
invalidated.

A stolen refresh token can be particularly important because it may be
used to obtain additional access tokens, depending on how the
authentication system is designed.

That is why refresh tokens should be handled carefully and why
applications may use expiration, revocation, rotation, and other
security controls.

## The complete flow in my understanding

After learning this topic, I understand the basic flow like this:

``` text
                 User
                  |
                  | Login
                  ↓
          Authentication Server
                  |
          ┌───────┴────────┐
          ↓                ↓
    Access Token     Refresh Token
          |
          ↓
    API Requests
          |
          ↓
    Access Token Expires
          |
          ↓
    Refresh Request
          |
          ↓
    New Access Token
          |
          ↓
    Continue API Requests
```

Once I looked at the complete flow, the difference between the two
tokens became much clearer.

## What I learned from this topic

Before learning about access tokens and refresh tokens, I mostly thought
about authentication as:

**Login → Check password → Allow access**

Now I understand that there is much more happening after login.

I learned:

1.  An access token is used to access protected resources.
2.  Access tokens are generally short-lived.
3.  A refresh token can be used to obtain a new access token.
4.  Refresh tokens need careful protection.
5.  Token expiration is an important part of authentication security.
6.  Authentication is a combination of security and session-management
    decisions.

The main thing I understood is that access tokens and refresh tokens
solve different problems. The access token is for accessing resources,
while the refresh token helps maintain the authenticated session without
making the user log in repeatedly.

## Final thoughts

This topic changed the way I look at login systems. Earlier, I only saw
the login page and assumed that authentication ended after entering the
password.

Now, when I use a web application, I understand that the application may
be using tokens in the background to authenticate my requests.

The simplest way I remember the concept is:

> **Access Token → used to access protected resources.**

> **Refresh Token → used to get a new access token.**

For me, understanding this difference made the overall authentication
flow much easier to understand.
